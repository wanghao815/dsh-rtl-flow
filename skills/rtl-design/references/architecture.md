# 从需求到可实施的架构合同

先确定本轮交付对象和使用场景，再决定模块。不要从旧项目的 PE、矩阵形状、数制或 SRAM 参数开始填新设计。

## 明确外部行为

1. 输入/输出协议：端口方向、位宽、单位、编码、时钟域、采样沿和稳定区间；传输的精确定义。流接口通常以 valid 与 ready 同沿成立为接受，项目可以有不同约定。
2. 复位：极性、同步/异步、释放方式，哪些状态与存储保留，复位中和复位后的输出可见性。
3. 工作负载：支持的配置范围、空/满和边界、持续/突发/单任务、非法请求策略、反压、仲裁公平性、异常和中止。
4. 性能：时钟目标、II（两个可接受输入间的最小周期数）、首结果延迟、事务完成条件及稳态/整任务吞吐。峰值须有足够长的合法工作负载验证。
5. 存储与边界：寄存器/推断 RAM/真实宏、端口、读延迟、掩码、字节序、逻辑/物理/使用容量。TB 初始化与可综合装载逻辑分清。
6. 平台与范围：目标器件/工艺、允许工具、主机资源、模型与规则的可获得性。本轮验证和后端覆盖写清。

## 形成微架构

画出模块连接、时钟域、寄存器边界、每个状态的唯一所有者和数据/元数据路径。对每条反馈边，明确生产者、消费者、最新状态在哪一拍被读到。给每个共享资源写吞吐预算；端口带宽不足时不得默认多泵时钟或时分复用。

对有数值路径的模块，先写运算图，再选位宽、舍入、饱和/回绕、下溢和异常策略。参考模型可以有不同归约顺序，但验收差异必须事前定义。对控制器使用可执行的协议状态模型，不引入无用的浮点误差预算。

对多个候选用同一工作负载比较正确性、误差、寄存器/算子资源、反馈路径、吞吐、面积、功耗条件和验证复杂度。估算与实测分开。必要时先综合并布线一个关键 leaf 或代表性子系统，再决定扩大规模或硬化边界；不能只凭宏数量判断物理验收规模。

查标准或论文时使用原始来源，保存标题、版本、链接及支撑位置。区分原文声称、文献已有结论、项目推导和未验证假设。迁移算法时重新核对项数、位宽、格式和约束，不把论文实验范围外的扩展称为已验证。

## 周期合同必须可采样

定义 E0 的受理条件，以及每沿 pre（采样前稳定值）和 post（寄存器更新稳定值）。逐项列输入接受、读取响应、内部提交、输出传输、最终副作用和 done；注明消费者最早可见的边沿。固定延迟设计推导起止公式并核对最短/最长工作负载；可反压设计写清哪些事件暂停、如何维护顺序和超时条件。

例如流式 FIFO 需决定满时若同拍 pop 是否允许 push、空时是否直通、输出是组合读还是寄存读。三者改变 ready、容量和可见延迟，不能用 testbench 的采样顺序偷偷决定。APB 寄存器块需确定 setup/access、PREADY 等待、PSLVERR、字节写选通及副作用触发沿。对 CPU 子模块，明确 flush、异常、stall 和提交优先级。

规格评审时交付系统架构图、关键 leaf 微架构图和周期/状态示例，并保留 SVG/PNG 与可编辑图源。图来自已确认合同；实测波形或 P&R 图另外标注来源和验证范围。
