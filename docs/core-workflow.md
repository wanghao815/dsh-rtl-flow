# 通用 RTL 插件核心流程

版本 0.2.0 · 2026-11-09。

## 1. 先识别任务，再选择入口

读取当前项目的规格、执行计划、关键决定、能力记录和实际报告，确认本次任务及授权。区分已确认约束、条件推导、候选方案和实测证据。当前暂停决定优先于历史队列，已确认结论不重复询问。

| 入口 | 起点与处理 |
| --- | --- |
| 新建 new | 确定交付范围，建立合同和最小工具链，逐级实现 |
| 接手 adopt | 清点现有源码、约束、测试和报告，审计基线，保留原文件，仅补缺项 |
| 修改 modify | 明确需求或缺陷的影响，复用未失效证据，重跑受影响检查 |
| 物理优化 eco | 固定原逻辑、约束和失败源，实施优化，复验等价、时序及相关物理检查 |
| 恢复 resume | 核对最新决定、进程、日志和最后完整检查点，在已有恢复授权内继续 |

工作入口不覆盖项目状态。接手与局部修改均无需从头重建工程；恢复入口也不自动解除暂停。

## 2. 主流程与阶段产物

| 阶段 | 核心工作与放行依据 |
| --- | --- |
| G0 规格 | 功能、接口、复位、合法配置、精度、周期/吞吐、存储、交付范围和资源预算 |
| G1 工具 | 实际调用入口、版本与材料锁定，正反例和代表性最小流程 |
| G2 参考 | 独立状态/数值模型、编码与布局、可重建输入、手算及边界检查 |
| G3 控制 | 接收、排队、反压、地址、标签、提交和完成的逐沿合同与检查 |
| G4 单元 | 关键 leaf RTL、功能/结构/适用形式检查，必要的早期物理探针 |
| G5 集成 | 复用同一已验证核心，逐层、逐配置集成并回归，检查真实输出和吞吐 |
| G6 实现 | 在匹配平台完成综合、布局、电网、CTS、布线和寄生提取 |
| G7 检查 | 对同一实际检查点进行 STA、DRC、LVS、天线、电源和约定覆盖检查 |
| G8 交付 | 受影响复验、源码与图源、报告、开放项、归档清单和接续入口 |

新项目按依赖推进；已有项目先验证哪些成果仍有效，再选择需执行的阶段。工具、参考、源码、约束或物理文件变化均须评估失效范围。RTL-only 明确排除物理阶段，ASIC 结果逐平台记录。

## 3. 按设计特性组合加载指导

特性可以叠加，模块名称不决定全部检查范围。算术加载运算图、位宽、舍入、合法域和数值验收；流处理加载反压、保持、顺序和守恒；协议加载状态、错误响应和副作用；多时钟加载 CDC/RDC 与复位释放；存储加载端口、延迟、掩码和容量；真实宏加载视图、端口、电源及同镜像回放；形式加载假设、可达性、证明范围与等价边界。

每个专题都说明进入条件、必要输入、操作、产物、判据和失败处理。只参数化已承诺的配置，不继承来源项目的阵列、数制、流水级数、容量、工艺或频率。

## 4. 从合同生成并验证 RTL

先固定外部行为、状态和寄存器归属、数值运算图及采样边沿，再实现最小关键单元。对齐仿真、综合和形式使用的源码、参数与宏定义。参考模型保持独立；测试从真实输出接口检查结果，覆盖手算、边界、固定 seed、故障检出和适用形式性质。

集成和修复保持已确认语义，不通过改门限、隐藏增级、降低接收率、缩容量或添加无依据时序例外使检查通过。架构图、关键单元图、通过用例波形和实际后端图均标明来源与范围。需要改变承诺时，提供具体证据和取舍，沿项目决定过程处理。

## 5. 用实际文件和原始报告支持验收

每条证据绑定当前设计配置摘要，以及实际合同、源码清单和参数文件。物理检查引用带角色和文件摘要的统一检查点清单，覆盖网表、SDC、寄生、库、宏、技术文件、规则、数据库和版图。标签相同不能代替这些输入相同。

读取原始工具报告，使用与检查类型匹配的解析器采集指标并核对预声明判据。合并回归日志保留全部测试汇总中的失败。缺字段、未知格式、缺模型、超时、退出中止和检查失败分别报告；不能只依据 Agent 填写的 passed 或命令退出零。文件失效或判据不满足时，相应关口及下游必须阻塞，并给出修复入口。

自动检查负责可核对的来源与指标，工程师仍复核规则、模型、抽象和适用范围。公开规则实验不称为制造签核。

## 6. 重任务前做真实资源预检

登记已有耗时、所有剩余任务及其依赖，使用代表性探针或有依据的保守上界估算各任务时间、峰值内存和磁盘增量。同步检测设备总内存、有效限制、当前可用内存，以及实际工作文件系统的可用空间，保留明确余量。

比较“已用时间＋剩余工作”与总时间预算，比较内存峰值/并发与设备和预算，比较已用磁盘/后续增长与预算和当前空间。估算缺失、探针过期或资源不足均阻止新增重任务，不能把未知值当作零。并行任务须计入叠加峰值，不能只按 CPU 核数并发。

授权内的单任务可用前台受控入口串行运行，记录原生退出、耗时和进程树内存；运行中检查时间、内存、磁盘与计划变化，退出后再次核对文件占用和剩余预算。任务及其依赖摘要变化后，旧完成记录不能继续作为执行依据。触及上限时保留日志和已有检查点，受控结束本任务的进程组并停止新增任务，报告继续、调整资源/规模/覆盖或收尾的影响。采样有瞬时盲区，仍需保守估算和余量；插件不代替操作系统硬资源限制。恢复与范围改变遵循新的明确决定。

## 7. 分开记录技术结果与交付结果

完整验收、约定范围交付、实验收尾分别表达，项目生命周期另记运行、暂停或归档。约定范围或收尾须绑定决定、原因和实际范围；原检查的失败、未完成、未支持和未覆盖项继续可见。

允许在完整物理验收尚未通过时完成实验归档，不把归档完成转换成技术通过。保留原版、选定基线、必要失败现场、外部依赖、开放项和恢复路径。

暂停后有明确收尾决定时，仅标为 closeout 的归档、清单核对等任务可以继续接受资源保护；设计实现任务保持停止，归档状态不允许继续执行任务。

## 8. 持续记录并交付可复核结果

AGENTS.md 管当前约束，TODO.md 管依赖与状态，key_milestone.md 管决定和阻塞，agent_ability_report.md 管尝试、失误、人工介入与复验，reports 保存原始证据。缺失计量写未记录，不编造 Token、费用、耗时或泛化结论。

交付说明实际改动、已执行检查、适用范围、图源和剩余事项。真实模型在 dsh 中完成新设计及至少一个小设计 RTL-to-GDS 的闭环验证，按用户决定留作 npm 正式发布前执行，本轮功能完善不宣称该验证已通过。独立 GitHub 源码仓库可以先公开供检查和试用。
